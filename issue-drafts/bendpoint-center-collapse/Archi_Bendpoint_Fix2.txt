This is a major find, and it substantially reframes what we're sitting on — in a good way, but it needs real reconciling before the draft goes anywhere.

The core mechanism we found was already independently discovered and partially fixed — by mwith, the same person who commented on #1237. From mwith's very first comment on this PR:

"if a bend point is located on the edge of the element then the drawing algorithm will render the connection from the center of the element to the attachment point... So in order not to make changes to the drawing algorithm then the attachment points will be adjusted so the start and end points is offset by 1."

That's the identical bug, described independently, in May. And notice the phrasing: mwith explicitly chose not to fix the underlying algorithm — just to route around it by nudging generated bendpoints a safe distance away. That's a scope decision, stated plainly, not an oversight.

This means the code I read from master several turns ago and proposed to "fix" was very likely mwith's already-negotiated, already-tested solution — not untouched original code. The midpoint-bendpoint logic I found and initially critiqued as imprecise is the outcome of real back-and-forth with Phillipus, converging on "one bendpoint at 50% between the two attachments" specifically because more precise placements caused a different, zoom-dependent instability that Phillipus found through actual testing:

"adding bend-points very close to the ends of a connection can lead to problems which become apparent when zooming in and out."

That's real, hands-on-verified fragility I had no way to know about, and it directly explains why the "obviously more precise" two-bendpoint fix I drafted might not hold up in practice the way it looks like it should on paper.

But here's why our finding isn't redundant — it's scoped differently, and mwith's own words confirm the gap: their fix only touches the XML import path — it makes newly-generated bendpoints avoid the trap when reading an Exchange Format file. It does nothing about the underlying anchor calculation itself, which mwith explicitly left alone. What Steve reproduced was live interactive editing — dragging a bendpoint by hand, then moving a shape — a completely different trigger path that never goes near the import code at all. The center-collapse mechanism is still live and reachable; it's just been fenced off on one specific entry point, not fixed at the source.
